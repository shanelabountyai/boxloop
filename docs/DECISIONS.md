# BoxLoop decisions

| Id | Decision | Why |
|---|---|---|
| D-001 | **A plan's price terms (`priceCents`, `interval`, `trialDays`) are fixed at creation.** Only the name is editable; repricing means creating a new plan and archiving the old one. A `BEFORE UPDATE` trigger (`plan_terms_immutable`, migration `20260930150049_plan_catalog`) enforces it, along with CHECKs `priceCents >= 0` and `trialDays` 0–365. Operators are `org.update` holders (owner, admin), since the template's permission list is template-owned. *Default taken 2026-09-30 (P0-1).* | Grandfathering (P0-1) falls out for free: a subscription points at its plan and its price can never move, so no price snapshot is needed on the subscription. Same model as Stripe Prices. Reversible: drop the trigger and add a snapshot column if in-place repricing is ever wanted. |
| D-002 | **Subscription state machine: two edges beyond the PRD's list, and the audit stream reused.** A trial can be cancelled straight to `cancelled` (nothing paid, so no paid-through to honour), and a failed trial-conversion charge moves `trialing → past_due` into dunning rather than needing a hop through `active`. Transitions audit into the template's append-only `AuditEvent` as `subscription.<event>` with `data {from, to}`; no separate table. Plan FK is `NO ACTION`, not `RESTRICT`, so an org delete cascades plans and subscriptions together. *Default taken 2026-10-01 (P0-2).* | The PRD lists the paid-subscription edges but is silent on a trial that cancels or whose first charge fails; both happen on day one of the billing run. `AuditEvent` is already immutable (INV-19) and has who/what/when; the event name carries voluntary vs dunning churn for P1-1. Reversible: drop an edge from the table in `src/subscriptions/state.ts`. |
| D-003 | **Time is passed in, not read from a clock.** Billing code (period math, signup, the billing run) takes the date as a parameter (`asOf`); `billing:run --date` and the 180-day `simulate` pass it in, defaulting to `now()` only at the command's edge. Dates are calendar days (UTC midnight, Postgres `date`). Billing dates are counted from a stored `billingAnchor` (trial end, or signup day without a trial), clamped to short months, never chained from the previous period. `nextBillingDate` is always the start of the first unpaid period. *Chosen by Shane 2026-10-01 (P0-3), over a shared mutable clock and an injected clock object.* | Pure functions of the date are testable without global state, and the PRD's `billing:run --date` already has this shape. The template's `advanceClock` sets an offset in template-owned code, and a clock object would be an abstraction with one implementation. Anchoring on trial end makes the conversion charge the first period start, so conversion and renewal are the same step: `periodFrom(billingAnchor, interval, nextBillingDate)`. |
| D-004 | **Billing run: every Subscription write stays in `transition.ts`, and a period is charged once by a database key.** Advancing the paid period is `advancePeriod()` in `transition.ts`, next to `transition()`, so the single-writer test stays unchanged. Each charge is a `ChargeAttempt` row, inserted and never updated, keyed unique on `(subscriptionId, periodStart, attempt)`. Attempt 1 is the daily run and dunning retries are 2, 3, ... (P0-6). The provider is charged first with the key `subId:periodStart:attempt` and the attempt is recorded afterwards, so a crash in between replays at the provider instead of charging twice. The run charges only `trialing` and `active` subscriptions, at most one period each per run. A failed charge moves the subscription to `past_due`, and its failed attempt row is where the dunning schedule starts. The mock charger approves everything until P0-6 adds a payment method that can decline. *Default taken 2026-10-01 (P0-4).* | One writer file keeps "who can change a subscription" answerable with a grep. A unique index makes idempotency hold even for two runs racing on the same date, where an application-level check alone would not. Charging before recording is the Stripe idempotency-key pattern. Reversible: narrow the single-writer test to writes of `status` and move `advancePeriod` out. |
| D-005 | **Dunning: retries are scheduled by day, numbered by attempt, and a member's retry counts.** Day 0 is the failed attempt 1 of the unpaid period (`nextBillingDate`). `runDunning(asOf)` makes at most one retry per subscription per run: the latest of days 1, 3 and 7 on or before `asOf` that no attempt has been made on or after. So a late run catches up with one charge rather than three, and a retry the member triggers by updating their card covers the scheduled day it followed. Every retry is the next attempt number, with the same unique key and charge-then-record order as D-004. On or after day 10 the subscription moves `past_due → cancelled` through `dunning_exhausted`, and that audit event name is what separates involuntary from voluntary churn. Each retry and the cancellation queue an email through the template's generic `notice` outbox template, because `templates.ts` is template-owned. The mock payment method is a `Subscription.card` column (`approves`/`declines`) written only by `setCard()` in `transition.ts`, and `mockCharger` reads it. `billing:run` runs billing and then dunning. *Default taken 2026-10-01 (P0-6).* | Scheduling by day rather than by attempt number keeps the PRD's day 1/3/7/10 calendar intact when member retries add attempts. Ordering billing before dunning means a charge that fails today opens dunning today, and its first retry still falls tomorrow. Reversible: switch to per-message templates once the foundation exposes a clone-side template registry. |
| D-006 | **Proration is by calendar day, each line rounds half-up on its own, and a downgrade's credit is a balance on the subscription.** `changePlan(actor, subId, toPlanId, asOf)` in `src/subscriptions/plan-change.ts` computes two line items over the paid period `[currentPeriodStart, currentPeriodEnd)`: a credit of `-old × remaining/period` and a charge of `new × remaining/period`, each through `prorateCents()` (integer half-up, `money.ts`), so a credit and a charge of the same size always match. The net is their sum. A positive net is charged at once, keyed `subId:plan:seq`, charged before it is recorded (D-004), and a decline changes nothing. A negative net is added to `Subscription.creditCents`. Each invoice (billing run and dunning retry) charges `price − min(credit, price)`, records the credit used as `ChargeAttempt.creditAppliedCents`, and takes it off the balance in `advancePeriod()`. An invoice that credit covers in full is not sent to the provider (`providerRef = "credit"`). Every change is a `PlanChange` row (inserted, never updated, unique `(subscriptionId, seq)`) holding the line items, and is audited as `subscription.plan_changed`. Only `trialing` (switch, no money) and `active` subscriptions can change plan, and only within the same interval. *Default taken 2026-10-01 (P0-5).* | Days are the unit that period math already uses, and per-line rounding is how Stripe shows proration, which keeps the invoice lines legible. A balance column is the smallest thing that carries a credit to "the next invoice" without an invoice table, and consuming it inside `advancePeriod()` means a credit is used only when a period is actually paid. Known limit: a credit is not applied against an upgrade charge in the same period, so a downgrade then upgrade collects cash now and returns it on the next invoice. Reversible: subtract the balance from the upgrade net. Month↔year switching stays P2. |
| D-007 | **A pause starts at once, moves the paid period N billing dates later, and ends on its own.** `pause(actor, subId, periods, asOf)` in `src/subscriptions/pause.ts` takes 1–3 periods and only an `active` subscription inside its paid period (the state machine refuses a trial). It sets `nextBillingDate` to the billing date N on from the one it replaces, moves `[currentPeriodStart, currentPeriodEnd)` the same N periods, and sets `pausedUntil = asOf + N intervals`. So the paid days not yet used when the member paused run from `pausedUntil` to the new billing date, with nothing charged or credited. `billingAnchor` does not change: skipping N billing dates is what the PRD's "the anchor shifts by the pause length" means, and it keeps a 31st anchor on the 31st. The daily billing run resumes every pause whose `pausedUntil` has come before it charges anything, so a resume day that is also a billing day bills once. `transition()` takes an optional `also` (extra fields plus the row values they were computed from), so the period fields and `pausedUntil` are written in the same guarded update as the status and audited with it. A CHECK holds `pausedUntil` set exactly while `status = 'paused'`. No early resume and no limit on pauses per year (the PRD's open question, V1 unlimited). *Default taken 2026-10-01 (P0-7).* | Moving the paid period keeps proration (P0-5) correct after a resume: the member is at the same point of a full-length period, so `prorationLines()` needs no pause case. Skipping billing dates rather than moving the anchor avoids a clamped short month (Feb 28) becoming the new anchor day. Known limit: when shifting clamps both the pause day and the period end to the same short-month day, at most the last 1–3 paid days are lost. Reversible: an early resume would move the schedule back by the whole periods not used, and is the next thing to add if members ask for it. |
| D-008 | **A cancellation ends on `currentPeriodEnd`, ended by the billing run, and a paused member cannot cancel yet.** Cancelling is `transition(actor, id, 'cancel')`: `active` → `pending_cancellation`, a trial → `cancelled` at once (D-002). `runBilling(asOf)` starts with a sweep that moves every `pending_cancellation` row whose `currentPeriodEnd <= asOf` through `period_ended`, before charging, so the renewal that day never happens; it sits next to the pause resume as one `sweep()` helper. `undoCancel(actor, subId, asOf)` in `src/subscriptions/cancel.ts` works only while `asOf < currentPeriodEnd`, so the end day is final even before that day's run, and an undone subscription renews on its unchanged `nextBillingDate`. The state machine has no `paused → cancel` edge: the member cancels once the pause ends on its own. *Default taken 2026-10-01 (P0-8).* | The paid-through date is the period already charged for, so no new field is needed. Refusing a paused cancel is the only option that neither gives away access nor money: going to `pending_cancellation` while paused would hand the paused months back as access until the moved period end, and cancelling at once would forfeit the unused paid days that the pause moved after it. Restore path: add `paused: 'pending_cancellation'` and, in the same `also`, set `pausedUntil: null` and `currentPeriodEnd = asOf + (currentPeriodEnd − pausedUntil)` days; undo then has to put `nextBillingDate` back on the anchor schedule. Do it if members ask to leave mid-pause. |
| D-009 | **The 180-day simulation is a deterministic script over the real billing code, in its own `sim` org, and it fails on a broken metric.** `simulate({ start, days })` in `src/subscriptions/simulate.ts` (`npm run simulate`, `--start`, `--days`) wipes and reseeds org `sim` with 50 members, member *i* signing up on day *i* into cohort *i* % 10 (steady, upgrade, downgrade, card never fixed, card fixed 2 days into dunning, a one-time soft decline, a 2-period pause, a period-end cancel with half undone, a trial cancel). Each day it signs up that day's members, runs `runBilling` and `runDunning` twice each (the reruns must charge nothing), and then runs each member's scripted action. All charges, including `updateCard` and `changePlan`, go through one sim charger that wraps `mockCharger`, adds the soft decline, and logs every successful charge. The report gives duplicate charges (ledger and provider), provider total against ledger total, dunning recovery (failed attempt 1s whose period was later paid), MRR at each month end (active, past_due and pending_cancellation; a yearly price counts as /12), and final statuses. The command exits 1 on a duplicate, a rerun that charged, or a ledger mismatch. Because the billing run is global, the sim refuses to run if any subscription exists outside its org. Audit rows from earlier runs stay (INV-19). `tests/integration/simulate.test.ts` checks the run against a hand tally. *Default taken 2026-10-01 (Phase 4).* | Scripted cohorts rather than random draws make every number hand-checkable, which is what the PRD's "correct vs. hand-tallied" asks for. Driving the real `runBilling`, `runDunning` and member functions with no simulation-only billing path means the sim tests what ships. The first run caught exactly that kind of gap: card updates and upgrades defaulted to `mockCharger` and skipped the provider log, and the reconciliation flagged $183.05. Reversible: give `runBilling`/`runDunning` an org filter to lift the empty-table rule. |
| D-010 | **Metrics are a replay of the `subscription.*` audit stream, keyed by business day.** Every subscription audit event now carries `on` (YYYY-MM-DD): `transition()`, `setCard()` and `switchPlan()` take a required `asOf`, and `subscription.created` also records `planId`. `AuditEvent.at` stays wall-clock, because `src/core/audit.ts` is template-owned and under the simulation every event lands within the same few seconds of real time. `replay()` in `src/subscriptions/metrics.ts` is a pure fold: it sorts events by `on` (stable, so same-day events keep their write order) and gives one row per requested day. Each row has MRR, paying and trialing counts, and since the previous row: trials converted, trials lost, voluntary churn and involuntary churn. MRR counts `active`, `past_due` and `pending_cancellation`, and a yearly price is /12 rounded half-up to the cent (`monthlyCents`, now shared with the simulation's snapshot). A trial converts the first time it reaches `active`, including a failed conversion that dunning recovers. A subscription cancelled before it ever paid is a lost trial, not churn. Churn is `dunning_exhausted` (involuntary) or any other cancel (voluntary) of a member who has paid. An event with no `on` throws instead of being skipped. The simulation replays its own month ends and fails if MRR or the paying count differs from the row snapshot. `/o/[org]/metrics` (operators, `org.update`) shows month ends through today. *Default taken 2026-10-01 (P1-1).* | The PRD asks for metrics "from events, not current state". Checking the replay against an independent read of the rows found a real defect on its first run: `card_updated` had no day, so the fold stalled at the first card change and reported 27 conversions instead of 38. Prices are immutable (D-001), so a plan id prices any point in history. No legacy events need a fallback, because the simulation refuses to run beside other subscriptions and every simulation run reseeds. Reversible: a materialised daily snapshot table, if replaying on every request ever gets slow. |
| D-011 | **A coupon is a percent off the next N paid invoices. It comes off before credit, survives a plan change, and proration prices both plans at the discount the period was paid at.** `applyCoupon(actor, subId, offBps, periods, asOf)` in `transition.ts` sets `Subscription.couponOffBps`/`couponPeriodsLeft`, audited as `subscription.coupon_applied`. It allows one live coupon at a time and refuses a cancelled subscription. `invoiceFor()` charges `price − discount − min(credit, price − discount)`, with the discount `percentOfCents()` (half-up, `money.ts`). It records `ChargeAttempt.discountCents`. `advancePeriod()` spends one coupon period only when a period is actually paid, so trials, declines and dunning retries spend nothing until the charge succeeds. It also stores the paid period's rate in `Subscription.paidOffBps`. `changePlan()` discounts both prices by `paidOffBps` before prorating (D-006 per-line rounding unchanged) and records it as `PlanChange.discountBps`. The coupon is left on the subscription and prices the new plan's invoices. Metrics MRR stays at list price. *Chosen by Shane 2026-10-01 (P1-2): discount then credit; survives; prorate at the discounted price.* | Discount-then-credit matches Stripe: a discount changes the price, a balance pays it, so the coupon never eats the credit. Prorating at the discounted price means a downgrade never credits more than was paid; at list price, a 25%-off member downgrading halfway would get 1000 back on 750 paid. `paidOffBps` is on the row rather than looked up from the ChargeAttempt, because a pause moves the paid period off its `periodStart` (D-007). Known limits: no coupon codes or catalog, no UI, a 100%-off invoice is recorded with `providerRef = "credit"`, and MRR ignores discounts. Reversible: subtract `paidOffBps` in `monthlyCents` if MRR should be net. |
| D-012 | **The trial-ending reminder is a step in the billing run, and it is queued once per subscription.** `runBilling(asOf)` runs `remindTrialsEnding(day)` after the resume and cancel sweeps and before charging. It picks every `trialing` subscription whose `nextBillingDate` (the conversion) is 1–3 days after `day` and that has no `TrialReminder` row yet. For each one it inserts `TrialReminder(subscriptionId PK, trialEndsOn, queuedOn)` with `skipDuplicates`, and queues an outbox email in the same transaction only if the row went in. The email uses the template's generic `notice` (templates are template-owned) and quotes `invoiceFor()`, so a coupon or credit shows in the amount. Migration `20261002000000_trial_reminder`, with `CHECK queuedOn < trialEndsOn`. *Chosen by Shane 2026-10-01 (P1-3), over a separate cron sweep.* | The billing run is already the daily clock and takes `asOf` (D-003), so the 180-day sim exercises the reminder without a second call, and no second place reads the time. A 1–3-day window rather than the exact day -3 means a skipped run still reminds the member. Conversion day itself is excluded, because by then it is too late to cancel. Keying on the subscription alone works because a subscription has one trial. The reminder is a separate table, not a column, so `transition.ts` stays the only `Subscription` writer (D-004). Delivery is the outbox's at-least-once; the queue step is exactly-once, and a test races two runs to prove it. |
| D-013 | **The independent MRR check is a LibreOffice sheet built from the sim's raw audit events, compared month end by month end with `replay()`.** `npm run mrr:check` (after `npm run simulate`) writes `out/mrr-check/sheet.csv`. The CSV holds one row per `subscription.*` event, sorted by subscription, then day, then write order, plus the sim's plans at list price. Formulas carry status and plan forward, price a yearly plan at `ROUND(price/12)`, mark each row superseded on the next event's day, and `SUMPRODUCT` MRR and the paying count at each month end. `soffice --headless` evaluates it, and the script exits 1 on any difference. First run: 5/5 month ends equal (Jan $555.00/18 → May $1,115.00/37). A mutation that drops `past_due` from `MRR_STATUSES` fails 2 of 5. *Default taken 2026-10-01; closes the PRD's last lagging metric.* | The check shares no code with `metrics.ts`. It gets only raw events and prices, and computes in a different engine with a different method (a validity interval per event, not a fold). The sim's own cross-check (D-010) reads the same `monthlyCents`. CSV with formulas needs no new dependency, since `soffice` is already installed. The script fails, not skips, if `soffice` is missing. Formulas use `;` separators (LibreOffice), so Excel shows them as text. Not in the vitest sweep, because it needs LibreOffice. Reversible: commit an `.ods` fixture if a reviewer wants the sheet without running anything. |
